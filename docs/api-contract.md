# Контракт інтеграції v1.0

Цей документ фіксує публічний інтерфейс етапу аналізу транскрипції.
Результат — звичайний Python `dict`; при серіалізації — JSON-об'єкт.
Клас `Analyzer` використовується для повторного використання завантажених
словників, але не є типом результату.

Машинозчитувана схема відповіді: [result.schema.json](../cefr_analyzer/data/result.schema.json)
(JSON Schema Draft 2020-12). Вона включена до Python-пакета:

```python
from cefr_analyzer import Analyzer, analyze, SCHEMA_VERSION, RESULT_SCHEMA_PATH
```

## Виклик

```python
result = analyze(text="I like reading.", words=None, ignore_terms=())

analyzer = Analyzer()
result = analyzer.analyze(text="I like reading.", words=None, ignore_terms=())
```

`data_dir` за замовчуванням указує на словники всередині пакета.
`config` — `ScoringConfig` або `None` для стандартних параметрів.
Параметри `ignore_terms`, `data_dir`, `config` у функції `analyze` передаються
тільки за іменем; у методі `Analyzer.analyze` таким є `ignore_terms`.
Створюйте один `Analyzer` для послідовної обробки багатьох текстів.

## Вхід

| Аргумент | Тип | Значення |
|---|---|---|
| `text` | `str \| None` | Англійська транскрипція |
| `words` | `list[dict]`, pandas DataFrame або `None` | Рядки `word`, `time_code` |
| `ignore_terms` | Послідовність рядків | Імена/назви, які треба явно виключити |

Обов'язкові поля кожного рядка `words`:

```json
{"word": "hello", "time_code": {"start": 1.0, "end": 1.4}}
```

- `word` — рядок; додаткові колонки дозволені й ігноруються.
- `time_code` — значення, яке зберігається без змін. Для JSON-обміну використовуйте
  рядок, скінченне число, `null`, список або об'єкт із JSON-сумісним вмістом.
  Python-об'єкти на кшталт `datetime` слід перетворити до виклику.
- Порядок рядків є порядком слів; сортування за таймкодом не виконується.
- `text` без `words` дозволений; списки `time_codes` у збігах будуть порожніми.
- Без `text` текст утворюється з колонки `word` через пробіл.
- Коли надано обидва входи, нормалізовані послідовності токенів мають збігатися.
  Регістр, пунктуація та підтримувані скорочення нормалізуються. Відсутні/зайві
  слова викликають `ValueError`; приблизної прив'язки таймкодів немає.
- Порожній вхід, зокрема `analyze()`, є допустимим і повертає звіт без рівня.
- Звичайні переноси між словами не змінюють семантичний результат.
  Символьні позиції залежать від фактичного вхідного тексту.

## Стабільні поля виходу

Усі наведені поля верхнього рівня присутні завжди. Порожні колекції
повертаються як `{}` або `[]`, а не як `None`.

| Поле | Тип | Призначення |
|---|---|---|
| `schema_version` | `str`, зараз `"1.0"` | Версія контракту |
| `assessment` | `dict` | Підсумкова приблизна оцінка |
| `word_levels` | `dict[str, str \| None]` | Слова/вирази та їхні словникові рівні |
| `statistics` | `dict` | Кількості, покриття й розподіли |
| `lexical_matches` | `list[dict]` | Входження слів/виразів із доказами |
| `grammar_matches` | `list[dict]` | Граматичні збіги з доказами |
| `unknown_words` | `list[dict]` | Унікальні невідомі слова, частоти, `level=None` |
| `unknown_occurrences` | `list[dict]` | Позиції невідомих слів |
| `automatic_matches` | `list[dict]` | Лексичні збіги з вибраною автоматичною оцінкою |
| `ignored` | `list[dict]` | Позиції явно проігнорованих токенів |
| `sources` | `dict` | Маніфест словників, URL та контрольні суми |
| `warnings` | `list[str]` | Інформаційні попередження |

### Загальний рівень

```python
result["assessment"]["level"]  # "A1", "A2", "B1", "B2", "C1", "C2" або None
```

Стабільні поля `assessment`:

- `level`: CEFR або `None`, якщо недостатньо надійних свідчень;
- `score`: число від 1 до 6 або `None` разом із `level`;
- `confidence`: `"low"` або `"medium"`, евристика достатності свідчень;
- `approximate`: завжди `True`;
- `lexical_score`, `grammar_score`: числа від 1 до 6;
- `eligible_lexical_units`, `eligible_grammar_matches`, `content_lexical_units`: цілі числа ≥ 0;
- `lexical_tails`, `grammar_tails`, `config`: діагностичні словники.

Внутрішній набір діагностичних параметрів може розширюватися. Для інтеграції
беріть `level` і `word_levels`, а не обчислюйте рівень із діагностичних полів.
`confidence` не є ймовірністю правильності. Значення рівнів можуть змінюватися
після покращення алгоритму або словників без зміни формату контракту.

### Слова та вирази

Приклад форми поля, не повний звіт:

```json
{"word_levels": {"cats": "A1", "turned down": "B1", "zqxvbling": null}}
```

Ключі — нормалізовані слова у формі з тексту, не обов'язково леми.
Повтори утворюють один ключ. Фрази мають один ключ із їхніх компонентів:
`turned it down → turned down`, а `it` може бути окремим ключем.
Компоненти знайденої фрази не дублюються як окремі слова для цього входження.
Ігноровані токени та числа пропускаються. Невідомі слова мають `None`/`null`.
У конфліктах вибирається нижчий словниковий CEFR. Порядок ключів не є контрактом.

`word_levels` включає також автоматичні/неоднозначні словникові оцінки.
Їхні позначки доступні в `lexical_matches`. Це поле не є переліком виключно
надійних свідчень, використаних для загальної оцінки.

### Позиції та докази

У кожного збігу/входження є:

```text
fragment: str
char_start: int             # включна позиція в Python-рядку
char_end: int               # виключна позиція в Python-рядку
token_indices: list[int]   # індекси нормалізованих токенів, від 0
sentence: int              # ідентифікатор сегмента, від 0
time_codes: list            # значення з вихідних рядків
```

Це не байтові позиції й не індекси DataFrame. Розкриті скорочення можуть мати
однакові вихідні символьні позиції. Один вихідний рядок не дублюється в
`time_codes` одного збігу. Для розділеної фрази `fragment` охоплює й розрив,
але індекси та таймкоди містять лише компоненти фрази.

Лексичний збіг додатково має `lemma`, `level`, `match`, `automatic`,
`ambiguous`, `level_conflict`, `sources`. Граматичний — `rule`, `level`
(може бути `None`), `ambiguous`, `sources`; додаткові ознаки залежать від правила.
`sources` усередині збігу — список записів походження, його детальна структура
залежить від джерела. Клієнт має зберігати її без припущення про єдиний формат.

## Помилки, CLI та сумісність

- Відсутня колонка, нестроковий `word`, нестроковий `text`, невідповідність
  тексту й таблиці: `ValueError` для підтримуваних контейнерів входу.
- Відсутній/недоступний файл словника: `OSError` або його підклас.
- Непідтримуваний Python-контейнер може викликати `TypeError`;
  контракт підтримує тільки описані вище типи.
- Попередження не замінюють винятки й не є машинними кодами помилок.
  Не розбирайте їхній текст як стабільний протокол.
- CLI `analyze --json` повертає той самий звіт у stdout, `--output` записує JSON
  у файл. Стандартний короткий stdout без `--json` не є стабільним API.
  Код завершення: `0` — успіх, `2` — неправильні дані/аргументи або файл.

У межах major-версії `1` не видаляємо й не перейменовуємо стабільні поля,
не змінюємо їхні типи або значення `None`. Нові необов'язкові поля дозволені;
клієнти мають ігнорувати незнайомі поля. Несумісна зміна вимагає major-версії `2`.
Оновлення словників, порогів і розпізнавання можуть змінити оцінки: версія
контракту не є версією алгоритму. Для відтворення зберігайте версію пакета/commit,
`assessment.config`, `sources` і вхідні дані.

Контрактні тести не фіксують очікуваний CEFR конкретного тексту, щоб
покращення аналітики не вимагали зміни інтеграції.
